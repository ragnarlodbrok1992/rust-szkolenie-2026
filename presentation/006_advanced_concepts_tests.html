Part 1

Generics

One piece of code for many types

The problem: duplicated code

fn largest_i32(items: &[i32]) -> &i32 {
    let mut largest = &items[0];
    for item in items {
        if item > largest {
            largest = item;
        }
    }
    largest
}
  • This finds the largest number in a slice.
  • To do the same for letters, you'd write largest_char with the same body, changing only i32 to char.
  • Two copies means every bug has to be fixed twice.

A generic function

The same body, with the type as a parameter <T>:

error[E0369]: binary operation `>` cannot be applied to type `&T`
  --> src/main.rs:17:17
   |
17 |         if item > largest {
   |            ---- ^ ------- &T
   |            |
   |            &T
   |
help: consider restricting type parameter `T` with trait `PartialOrd`
   |
14 | fn largest_without_bound<T: std::cmp::PartialOrd>(items: &[T]) -> &T {
   |                           ++++++++++++++++++++++
  • <T> declares a type parameter: "some type, chosen by the caller".
  • Not every type can be compared with >, so the compiler refuses. Its help shows the fix.

Trait bounds

fn largest<T: PartialOrd>(items: &[T]) -> &T {
    let mut largest = &items[0];
    for item in items {
        if item > largest {
            largest = item;
        }
    }
    largest
}

let numbers = [34, 50, 25, 100, 65];
let letters = ['y', 'm', 'a', 'q'];
println!("{} {}", largest(&numbers), largest(&letters));
Output 
100 y
  • T: PartialOrd is a trait bound: any type that can be compared.
  • One function now works for i32, char, and any other comparable type.
  • No runtime cost: the compiler generates a separate copy for each type you use.

Generic structs

struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}

let integer_point = Point { x: 5, y: 10 };
let float_point = Point { x: 1.0, y: 4.0 };
  • Structs and enums can have type parameters too.
  • impl<T> writes methods once for every Point<T>.
  • Both fields share one T, so Point { x: 5, y: 4.0 } fails: E0308 expected integer, found floating-point number.
  • Option<T> and Result<T, E> are generic enums like this.
Part 2

Traits

Behavior that different types share

Defining and implementing a trait

trait Describe {
    fn describe(&self) -> String;
}

struct Dog {
    name: String,
}

impl Describe for Dog {
    fn describe(&self) -> String {
        format!("{} the dog", self.name)
    }
}
  • A trait lists methods that a type promises to provide.
  • impl Describe for Dog keeps that promise for Dog.
  • Leave a method out and you get E0046 not all trait items implemented, missing: describe.
  • Traits are like interfaces in other languages.

Enums and default methods

impl Describe for Weather {
    fn describe(&self) -> String {
        match self {
            Weather::Sunny => String::from("a sunny day"),
            Weather::Rainy => String::from("a rainy day"),
        }
    }
}
  • Any type can implement a trait, enums included.
trait Describe {
    fn describe(&self) -> String;

    fn shout(&self) -> String {
        self.describe().to_uppercase()
    }
}
Weather::Rainy.shout() 
A RAINY DAY
  • A default method has a body in the trait. Types get it for free, and can override it.

Traits as parameters

fn print_description(item: &impl Describe) {
    println!("{}", item.describe());
}

fn print_twice<T: Describe>(item: &T) {
    println!("{} / {}", item.describe(), item.shout());
}

fn print_and_copy<T>(item: &T) -> T
where
    T: Describe + Clone,
{
    println!("{}", item.describe());
    item.clone()
}
  • &impl Describe accepts any type that implements the trait.
  • <T: Describe> says the same thing in longer form.
  • + requires several traits.
  • where moves long bounds out of the signature.

Display: printing with {}

use std::fmt;

struct Temperature {
    degrees: f64,
}

impl fmt::Display for Temperature {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{:.1}°C", self.degrees)
    }
}

let temperature = Temperature { degrees: 21.456 };
println!("{temperature}");
Output 
21.5°C
  • {} needs the standard trait Display. Dog has none: E0277 Dog doesn't implement std::fmt::Display.
  • write! works like format!, but writes into f.
  • You also get .to_string() for free.

derive explained

#[derive(Debug, Clone, PartialEq, Default)]
struct Settings {
    volume: u8,
    muted: bool,
}

let original = Settings::default();
let copy = original.clone();
println!("{copy:?} {}", copy == original);
Output 
Settings { volume: 0, muted: false } true
  • #[derive(…)] writes the impl blocks for standard traits for you.
  • This is what #[derive(Debug)] did in chapter 5.
  • Default uses each field's default: 0, false, an empty String.

impl Trait vs dyn Trait

let items: Vec<Box<dyn Describe>> = vec![
    Box::new(Dog {
        name: String::from("Rex"),
    }),
    Box::new(Weather::Rainy),
];
for item in &items {
    println!("{}", item.describe());
}
Output 
Rex the dog
a rainy day
  • impl Trait: one concrete type, picked at compile time.
  • dyn Trait: any type that implements the trait, picked at runtime. That's how one Vec can hold both a Dog and a Weather.
  • Box stores a value on the heap (chapter 3). It's needed because the types have different sizes.
Part 3

Error handling

Two kinds of errors

Unrecoverable: panic!

A bug, or a state that should be impossible. The program stops.

Recoverable: Result

Something that can reasonably fail: user input, files, the network. The caller decides what to do.

enum Result<T, E> {
    Ok(T),
    Err(E),
}
  • Ok holds the value, and Err holds the error.
  • Like Option, you can't use the value without handling the error case.

Handling a Result

let inputs = ["42", "4x2"];
for input in inputs {
    match input.parse::<i32>() {
        Ok(number) => println!("number: {number}"),
        Err(error) => println!("error: {error}"),
    }
}
Output 
number: 42
error: invalid digit found in string
  • parse turns text into a number and returns a Result.
  • ::<i32> says which type to parse into.
  • match handles both outcomes, just as with Option.

unwrap and expect

let number = "4x2".parse::<i32>().unwrap();
let age = "4x2".parse::<i32>().expect("age must be a number");
Panic messages 
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
age must be a number: ParseIntError { kind: InvalidDigit }
  • Both return the value from Ok, or panic on Err.
  • expect adds your message, which makes the panic much easier to understand.
  • Fine in tests and quick experiments. In real code, prefer handling the error.

The ? operator

use std::num::ParseIntError;

fn add_numbers(first: &str, second: &str) -> Result<i32, ParseIntError> {
    let a = first.parse::<i32>()?;
    let b = second.parse::<i32>()?;
    Ok(a + b)
}
println!("{:?}", add_numbers("2", "40"));
println!("{:?}", add_numbers("2", "x"));
Output 
Ok(42)
Err(ParseIntError { kind: InvalidDigit })
  • ? on Ok gives the value. On Err, it returns the error from the function immediately.
  • It replaces a whole match with one character.

? in main

error[E0277]: the ? operator can only be used in a function that returns Result or Option

 --> src/main.rs:2:37
  |
1 | fn main() {
  | --------- this function should return `Result` or `Option` to accept `?`
2 |     let number = "42".parse::<i32>()?;
  |                                     ^ cannot use the `?` operator in a function that returns `()`
fn main() -> Result<(), ParseIntError> {
    let number = "4x2".parse::<i32>()?;
    println!("{number}");
    Ok(())
}
Output 
Error: ParseIntError { kind: InvalidDigit }
  • main may return a Result. An Err is printed, and the program exits with an error code.

Your own error type

#[derive(Debug)]
enum AgeError {
    NotANumber,
    TooOld(u32),
}

impl fmt::Display for AgeError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AgeError::NotANumber => write!(f, "age must be a number"),
            AgeError::TooOld(age) => write!(f, "{age} is too old"),
        }
    }
}
  • An enum lists everything that can go wrong. Callers can match on it.
  • Display gives each error a readable message.
  • Debug lets it be printed with {:?}, for example when main returns it.

Returning your own errors

fn parse_age(input: &str) -> Result<u32, AgeError> {
    let age = input.parse::<u32>().map_err(|_| AgeError::NotANumber)?;
    if age > 150 {
        return Err(AgeError::TooOld(age));
    }
    Ok(age)
}

for input in ["30", "abc", "200"] {
    match parse_age(input) {
        Ok(age) => println!("age: {age}"),
        Err(error) => println!("error: {error}"),
    }
}
Output 
age: 30
error: age must be a number
error: 200 is too old
  • .map_err(…) turns the parse error into your own error, using a closure (chapter 5).
  • return Err(…) reports your own failure.

panic! or Result?

Return a Result when

  • failure is a normal possibility: user input, files, the network
  • the caller should decide what happens next
  • you're writing a library for others

Converting

  • option.ok_or("no value") turns an Option into a Result.
  • result.ok() turns a Result into an Option.

Panic when

  • it's a bug: a broken assumption, a state that should be impossible
  • continuing would be wrong or unsafe
  • you're writing a test, an example, or a prototype (unwrap, expect)
Part 4

Testing

Letting the computer check your code

A first test

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn largest_finds_biggest_number() {
        assert_eq!(*largest(&[3, 9, 4]), 9);
    }
}
  • #[test] marks a function as a test.
  • mod tests is a module: a named group of code inside the file.
  • use super::*; brings in everything from the file around it, so the test can call largest.
  • #[cfg(test)] compiles the module only for cargo test.

Running tests

$ cargo test
running 7 tests
test tests::adds_valid_numbers ... ok
test tests::largest_finds_biggest_number ... ok
test tests::parse_age_accepts_valid_age ... ok
test tests::parse_age_rejects_age_over_150 ... ok
test tests::largest_of_empty_slice_panics - should panic ... ok
test tests::temperature_displays_one_decimal ... ok
test tests::parse_age_rejects_text ... ok
test result: ok. 7 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
  • cargo test compiles the program with its tests and runs every #[test] function.
  • A test passes if it finishes without panicking.
  • Tests run in parallel, so their order changes from run to run.

Assertions

assert_eq!(parse_age("30").unwrap(), 30);
assert!(matches!(parse_age("abc"), Err(AgeError::NotANumber)));
assert_ne!(temperature.to_string(), "21.456°C");
assert!(result.is_err(), "expected an error for 200, got {result:?}");
MacroPanics when
assert!(condition)the condition is false
assert_eq!(left, right)the values differ, and it shows both
assert_ne!(left, right)the values are equal
matches!(value, pattern)never: it returns a bool, which you pass to assert!

Any assertion takes an extra message with {} placeholders, shown when it fails.

When a test fails

---- tests::largest_of_letters_is_wrong_on_purpose stdout ----

thread 'tests::largest_of_letters_is_wrong_on_purpose' (22860) panicked at src/main.rs:293:9:
assertion `left == right` failed
  left: 'z'
 right: 'k'

test result: FAILED. 7 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
  • Each failure shows the test name, the file and line, and both values.
  • left is the first argument (here, what the code produced), right is the second (what you expected).
  • The other tests still run, so one failure doesn't hide the others.

Testing panics and errors

#[test]
#[should_panic(expected = "index out of bounds")]
fn largest_of_empty_slice_panics() {
    largest::<i32>(&[]);
}
  • #[should_panic] passes only if the test panics.
  • expected checks that the panic message contains this text.
#[test]
fn adds_valid_numbers() -> Result<(), ParseIntError> {
    assert_eq!(add_numbers("2", "40")?, 42);
    Ok(())
}
  • A test can return a Result and use ?.
  • It fails if it returns an Err.

Choosing which tests to run

CommandWhat it runs
cargo testAll tests
cargo test parse_ageOnly tests whose name contains parse_age (3 of 7 here)
cargo test -- --show-outputAll tests, and also shows what passing tests printed
  • Integration tests live in a tests/ folder and use your code from outside, like a user would.
  • Documentation tests are code examples in /// comments, and cargo test runs them too.
  • Both need a library crate (src/lib.rs), so they're beyond this course's single-file examples.

Effective tests

One behavior per test

When it fails, you know exactly what broke.

Names that describe the behavior

parse_age_rejects_text beats test3.

Edge cases

Empty input, zero, the limits (150 and 151), unusual characters.

The error paths too

Check that bad input gives the right error, not only that good input works.

Fast and independent

No test should depend on another one or on the order they run in.

Tests as documentation

Reading the tests should tell you what the code is supposed to do.

Arrange, act, assert

#[test]
fn parse_age_rejects_age_over_150() {
    let input = "200";

    let result = parse_age(input);

    assert!(result.is_err(), "expected an error for 200, got {result:?}");
}
  • Arrange: prepare the input.
  • Act: call the code you're testing, once.
  • Assert: check the result, with a message that explains the failure.
  • Blank lines between the steps make the structure easy to see.

Summary

  • Generics write code once for many types. Trait bounds say what those types must be able to do.
  • Traits define shared behavior. derive implements standard traits, and dyn mixes types at runtime.
  • Result represents recoverable errors. ? passes them to the caller, and your own enum describes them.
  • panic! is for bugs. unwrap and expect are for tests and prototypes.
  • #[test], assertions, and cargo test check behavior. Good tests are small, well named, and cover the error paths.

Część 1

Typy generyczne

Jeden kod dla wielu typów

Problem: powielony kod

fn largest_i32(items: &[i32]) -> &i32 {
    let mut largest = &items[0];
    for item in items {
        if item > largest {
            largest = item;
        }
    }
    largest
}
  • Ta funkcja znajduje największą liczbę w wycinku.
  • Żeby zrobić to samo dla liter, trzeba by napisać largest_char z tym samym ciałem, zmieniając tylko i32 na char.
  • Dwie kopie oznaczają, że każdy błąd trzeba poprawiać dwa razy.

Funkcja generyczna

To samo ciało, a typ staje się parametrem <T>:

error[E0369]: binary operation `>` cannot be applied to type `&T`
  --> src/main.rs:17:17
   |
17 |         if item > largest {
   |            ---- ^ ------- &T
   |            |
   |            &T
   |
help: consider restricting type parameter `T` with trait `PartialOrd`
   |

  • <T> deklaruje parametr typu: „jakiś typ, wybrany przez wywołującego”.
  • Nie każdy typ da się porównać przez >. Linia help: pokazuje poprawkę.

Ograniczenia traitów (trait bounds)

fn largest<T: PartialOrd>(items: &[T]) -> &T {
    let mut largest = &items[0];
    for item in items {
        if item > largest {
            largest = item;
        }
    }
    largest
}

let numbers = [34, 50, 25, 100, 65];
let letters = ['y', 'm', 'a', 'q'];
println!("{} {}", largest(&numbers), largest(&letters));
Wynik 
100 y
  • T: PartialOrd to ograniczenie traitu: dowolny typ, który da się porównywać.
  • Jedna funkcja działa teraz dla i32, char i każdego innego porównywalnego typu.
  • Bez kosztów w czasie działania: kompilator generuje osobną kopię dla każdego użytego typu.

Struktury generyczne

struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}

let integer_point = Point { x: 5, y: 10 };
let float_point = Point { x: 1.0, y: 4.0 };
  • Struktury i enumy też mogą mieć parametry typu.
  • impl<T> pisze metody raz dla każdego Point<T>.
  • Oba pola dzielą jedno T, więc Point { x: 5, y: 4.0 } się nie skompiluje: E0308 expected integer, found floating-point number.
  • Option<T> i Result<T, E> to właśnie takie enumy generyczne.
Część 2

Traity

Zachowanie wspólne dla różnych typów

Definiowanie i implementowanie traitu

trait Describe {
    fn describe(&self) -> String;
}

struct Dog {
    name: String,
}

impl Describe for Dog {
    fn describe(&self) -> String {
        format!("{} the dog", self.name)
    }
}
  • Trait wymienia metody, które typ obiecuje dostarczyć.
  • impl Describe for Dog spełnia tę obietnicę dla Dog.
  • Pominięcie metody daje E0046 not all trait items implemented, missing: describe.
  • Traity przypominają interfejsy z innych języków.

Enumy i metody domyślne

impl Describe for Weather {
    fn describe(&self) -> String {
        match self {
            Weather::Sunny => String::from("a sunny day"),
            Weather::Rainy => String::from("a rainy day"),
        }
    }
}
  • Trait może zaimplementować każdy typ, także enum.
trait Describe {
    fn describe(&self) -> String;

    fn shout(&self) -> String {
        self.describe().to_uppercase()
    }
}
Weather::Rainy.shout() 
A RAINY DAY
  • Metoda domyślna ma ciało w traicie. Typy dostają ją za darmo i mogą ją nadpisać.

Traity jako parametry

fn print_description(item: &impl Describe) {
    println!("{}", item.describe());
}

fn print_twice<T: Describe>(item: &T) {
    println!("{} / {}", item.describe(), item.shout());
}

fn print_and_copy<T>(item: &T) -> T
where
    T: Describe + Clone,
{
    println!("{}", item.describe());
    item.clone()
}
  • &impl Describe przyjmuje dowolny typ, który implementuje trait.
  • <T: Describe> mówi to samo w dłuższej formie.
  • + wymaga kilku traitów naraz.
  • where przenosi długie ograniczenia poza sygnaturę.

Display: wypisywanie przez {}

use std::fmt;

struct Temperature {
    degrees: f64,
}

impl fmt::Display for Temperature {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{:.1}°C", self.degrees)
    }
}

let temperature = Temperature { degrees: 21.456 };
println!("{temperature}");
Wynik 
21.5°C
  • {} wymaga standardowego traitu Display. Dog go nie ma: E0277 Dog doesn't implement std::fmt::Display.
  • write! działa jak format!, ale pisze do f.
  • W zestawie dostajesz też .to_string().

Część 3

Obsługa błędów

Dwa rodzaje błędów

Nienaprawialne: panic!

Błąd w programie albo stan, który nie powinien wystąpić. Program się zatrzymuje.

Naprawialne: Result

Coś, co może się nie udać w normalnych warunkach: dane od użytkownika, pliki, sieć. Wywołujący decyduje, co dalej.

enum Result<T, E> {
    Ok(T),
    Err(E),
}
  • Ok zawiera wartość, a Err zawiera błąd.
  • Tak jak przy Option, nie użyjesz wartości bez obsłużenia błędu.

Obsługa Result

let inputs = ["42", "4x2"];
for input in inputs {
    match input.parse::<i32>() {
        Ok(number) => println!("number: {number}"),
        Err(error) => println!("error: {error}"),
    }
}
Wynik 
number: 42
error: invalid digit found in string
  • parse zamienia tekst na liczbę i zwraca Result.
  • ::<i32> mówi, na jaki typ zamieniać.
  • match obsługuje oba wyniki, tak jak przy Option.

unwrap i expect

let number = "4x2".parse::<i32>().unwrap();
let age = "4x2".parse::<i32>().expect("age must be a number");
Komunikaty paniki 
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
age must be a number: ParseIntError { kind: InvalidDigit }
  • Obie metody zwracają wartość z Ok albo panikują przy Err.
  • expect dodaje twój komunikat, dzięki czemu panika jest dużo łatwiejsza do zrozumienia.
  • Dobre w testach i szybkich eksperymentach. W prawdziwym kodzie lepiej obsłużyć błąd.

Operator ?

use std::num::ParseIntError;

fn add_numbers(first: &str, second: &str) -> Result<i32, ParseIntError> {
    let a = first.parse::<i32>()?;
    let b = second.parse::<i32>()?;
    Ok(a + b)
}
println!("{:?}", add_numbers("2", "40"));
println!("{:?}", add_numbers("2", "x"));
Wynik 
Ok(42)
Err(ParseIntError { kind: InvalidDigit })
  • ? przy Ok daje wartość. Przy Err od razu zwraca błąd z funkcji.
  • Zastępuje cały match jednym znakiem.

  • main może zwracać Result. Err zostaje wypisany, a program kończy się kodem błędu.

Własny typ błędu

#[derive(Debug)]
enum AgeError {
    NotANumber,
    TooOld(u32),
}

impl fmt::Display for AgeError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AgeError::NotANumber => write!(f, "age must be a number"),
            AgeError::TooOld(age) => write!(f, "{age} is too old"),
        }
    }
}
  • Enum wymienia wszystko, co może pójść źle. Wywołujący może zrobić na nim match.
  • Display daje każdemu błędowi czytelny komunikat.
  • Debug pozwala wypisać go przez {:?}, np. gdy zwraca go main.

Zwracanie własnych błędów

fn parse_age(input: &str) -> Result<u32, AgeError> {
    let age = input.parse::<u32>().map_err(|_| AgeError::NotANumber)?;
    if age > 150 {
        return Err(AgeError::TooOld(age));
    }
    Ok(age)
}

for input in ["30", "abc", "200"] {
    match parse_age(input) {
        Ok(age) => println!("age: {age}"),
        Err(error) => println!("error: {error}"),
    }
}
Wynik 
age: 30
error: age must be a number
error: 200 is too old
  • .map_err(…) zamienia błąd parsowania na twój własny błąd za pomocą domknięcia (rozdział 5).
  • return Err(…) zgłasza twoją własną porażkę.

panic! czy Result?

Zwracaj Result, gdy

  • porażka jest normalną możliwością: dane od użytkownika, pliki, sieć
  • to wywołujący powinien zdecydować, co dalej
  • piszesz bibliotekę dla innych

Konwersje

  • option.ok_or("no value") zamienia Option na Result.
  • result.ok() zamienia Result na Option.

Panikuj, gdy

  • to błąd w programie: złamane założenie, stan, który nie powinien wystąpić
  • kontynuowanie byłoby błędne albo niebezpieczne
  • piszesz test, przykład albo prototyp (unwrap, expect)

Testowanie

Niech komputer sprawdza twój kod

Pierwszy test

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn largest_finds_biggest_number() {
        assert_eq!(*largest(&[3, 9, 4]), 9);
    }
}
  • #[test] oznacza funkcję jako test.
  • mod tests to moduł: nazwana grupa kodu wewnątrz pliku.
  • use super::*; udostępnia wszystko z otaczającego pliku, więc test może wywołać largest.
  • #[cfg(test)] kompiluje moduł tylko dla cargo test.

Skuteczne testy

Jedno zachowanie na test

Gdy test nie przejdzie, wiesz dokładnie, co się zepsuło.

Nazwy opisujące zachowanie

parse_age_rejects_text jest lepsze niż test3.

Przypadki brzegowe

Puste dane, zero, granice (150 i 151), nietypowe znaki.

Także ścieżki błędów

Sprawdzaj, że złe dane dają właściwy błąd, a nie tylko, że dobre działają.

Szybkie i niezależne

Żaden test nie powinien zależeć od innego ani od kolejności wykonania.

Testy jako dokumentacja

Testy powinny mówić, co kod ma robić.

Przygotuj, wykonaj, sprawdź

#[test]
fn parse_age_rejects_age_over_150() {
    let input = "200";

    let result = parse_age(input);

    assert!(result.is_err(), "expected an error for 200, got {result:?}");
}
  • Przygotuj (arrange): przygotuj dane wejściowe.
  • Wykonaj (act): wywołaj testowany kod, jeden raz.
  • Sprawdź (assert): sprawdź wynik, z komunikatem wyjaśniającym porażkę.
  • Puste linie między krokami pokazują strukturę.

Podsumowanie

  • Typy generyczne pozwalają napisać kod raz dla wielu typów. Ograniczenia traitów mówią, co te typy muszą umieć.
  • Traity definiują wspólne zachowanie. derive implementuje traity standardowe, a dyn łączy typy w czasie działania.
  • Result reprezentuje błędy naprawialne. ? przekazuje je wywołującemu, a własny enum je opisuje.
  • panic! jest dla błędów w programie. unwrap i expect są dla testów i prototypów.
  • #[test], asercje i cargo test sprawdzają zachowanie. Dobre testy są małe, dobrze nazwane i obejmują ścieżki błędów.
